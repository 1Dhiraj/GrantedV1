# Pattern Learning

Look back over what the user has actually done and said, find the things that
repeat, and write down the few that are worth acting on.

The point is to stop re-learning the same preference every week. The risk is the
opposite failure, and it is worse: recording a one-off as a standing rule, then
applying it forever to someone who never asked for it. A wrong preference is
harder to notice than no preference, because it quietly shapes every future
reply and never announces itself.

So the bar is evidence, not plausibility. **Three occurrences is a pattern. One
is a Tuesday.**

## When to Use

- A scheduled review (weekly or after N sessions) — this is the main use.
- The user says "you always get this wrong" or "I've told you this before."
- After a long session with repeated corrections on the same axis.

Don't use for: a preference the user just stated directly — record that as a
fact immediately, it needs no evidence gathering. And don't use it to invent a
profile of someone from thin material.

## Procedure

### 1. Set the window and the sources

Decide what period you are reviewing and which sources you can actually read:
session history, memory files, the workspace, prior corrections. State the
window.

Done when the period and the readable sources are named.

### 2. Collect candidates, with their evidence

Go looking for repetition in these specific places — they are where real
preferences live:

- **Corrections.** The user changing what you did is the strongest signal
  available. What axis did they correct, and which direction?
- **Restated requests.** Asking for the same thing twice means it was not
  delivered the first time.
- **Consistent choices.** Same tool, same format, same level of detail, chosen
  repeatedly when alternatives existed.
- **Timing.** Work that recurs on a schedule.
- **Explicit statements.** "I prefer", "don't", "always", "from now on."

For each candidate, record the occurrences — when, and what happened. A
candidate with no list of occurrences is not a candidate.

Done when every candidate has its evidence attached.

### 3. Apply the bar

Keep a candidate only if **all** of these hold:

- It happened at least three times, or was stated explicitly once.
- The occurrences are independent — three corrections in one session about one
  document is one occurrence, not three.
- It would change what you do next time. A pattern that changes nothing is
  trivia.
- It is about the user's preference, not about a task that happened to recur.

Discard everything else. Discarding is the normal outcome; most candidates fail
this.

Done when each candidate is kept with its reason or discarded with its reason.

### 4. Check against what is already recorded

Read existing memory before writing. For each kept pattern:

- **New** — record it.
- **Confirms existing** — strengthen it; note the extra evidence, do not
  duplicate the entry.
- **Contradicts existing** — this is the important case. The user changed their
  mind, or the old entry was wrong. Prefer the recent evidence, replace the old
  entry, and say in the entry that it superseded something.

Never leave two entries that contradict each other. That is worse than having
neither.

Done when every kept pattern is reconciled with what was already there.

### 5. Write it down so it can be undone

Each recorded pattern states: what the preference is, what evidence supports it,
when it was recorded, and how to apply it. Keep it to a sentence or two.

Write the evidence because a future session needs to judge whether the pattern
still holds. A bare assertion cannot be re-evaluated, only obeyed.

Done when each entry carries its evidence and its date.

### 6. Tell the user what you learned

Report what was recorded, in plain language, and invite correction. One short
list.

A preference the user does not know you hold is one they cannot correct, and a
wrong one will then shape everything quietly. This step is what makes the whole
skill safe to run.

Done when the user has seen the list.

## Reporting Rules

- Never record a pattern about a protected characteristic, health, finances, or
  personal relationships. Preferences about _work_ only.
- Never infer a pattern from a single emphatic moment. Frustration is not a
  preference.
- Prefer "prefers X when Y" over "always does X". Scoped patterns survive;
  absolute ones get in the way.
- If the evidence is thin but the signal feels strong, record nothing and say so.
  Thin evidence is exactly how a wrong standing rule gets created.
